# HALLAZGOS

## Flujo observado de web

No existe `docs/ENDPOINTS.md` en el workspace. Lo siguiente describe el contrato observado en el cliente; no representa un contrato acordado con los servicios.

- Login: `POST http://localhost:8080/auth/login` con `username`, `password` y `client`. `AuthService` guarda token, usuario y preferencias en `localStorage` cuando la respuesta contiene token; luego el componente navega a `/dashboard`. Evidencia: [web/src/app/login/login.component.ts:40](web/src/app/login/login.component.ts#L40), [web/src/app/services/auth.service.ts:25](web/src/app/services/auth.service.ts#L25), [web/src/app/services/auth.service.ts:31](web/src/app/services/auth.service.ts#L31), [web/src/app/services/auth.service.ts:62](web/src/app/services/auth.service.ts#L62), [web/src/app/login/login.component.ts:46](web/src/app/login/login.component.ts#L46).
- Dashboard: obtiene token y usuario mediante `AuthService`; sin token navega a `/login`. Con token solicita `GET http://localhost:8000/api/tasks?owner=<username>` y envía `Authorization: Bearer <token>`, filtra tareas `ARCHIVED`, prepara etiquetas y ordena la lista. Evidencia: [web/src/app/dashboard/dashboard.component.ts:45](web/src/app/dashboard/dashboard.component.ts#L45), [web/src/app/dashboard/dashboard.component.ts:46](web/src/app/dashboard/dashboard.component.ts#L46), [web/src/app/dashboard/dashboard.component.ts:48](web/src/app/dashboard/dashboard.component.ts#L48), [web/src/app/dashboard/dashboard.component.ts:53](web/src/app/dashboard/dashboard.component.ts#L53), [web/src/app/services/tasks.service.ts:9](web/src/app/services/tasks.service.ts#L9), [web/src/app/services/tasks.service.ts:10](web/src/app/services/tasks.service.ts#L10).
- Cierre de sesión: elimina token y usuario localmente y navega a `/login`; no se observa una llamada de logout al servidor. Evidencia: [web/src/app/dashboard/dashboard.component.ts:83](web/src/app/dashboard/dashboard.component.ts#L83), [web/src/app/dashboard/dashboard.component.ts:84](web/src/app/dashboard/dashboard.component.ts#L84), [web/src/app/services/auth.service.ts:56](web/src/app/services/auth.service.ts#L56), [web/src/app/services/auth.service.ts:57](web/src/app/services/auth.service.ts#L57), [web/src/app/services/auth.service.ts:58](web/src/app/services/auth.service.ts#L58).

## Candidatos de discovery web

Todos los siguientes permanecen sujetos a revisión humana. Las pruebas indicadas son propuestas de validación; no se ejecutaron durante este discovery.

### H-WEB-01: Token bearer almacenado en `localStorage`
- Estado: CANDIDATO
- Evidencia: `web/src/app/services/auth.service.ts:62` escribe el token; `web/src/app/services/auth.service.ts:49` lo lee; `web/src/app/dashboard/dashboard.component.ts:45` consume esa lectura; `web/src/app/services/tasks.service.ts:10` lo envía como Bearer.
- Impacto: una inyección de script exitosa en el mismo origen podría leer el token y exponer la sesión; no se observó explotación.
- Prioridad propuesta: media.
- Contrato potencialmente afectado: sesión iniciada por `POST /auth/login` y autorización de `GET /api/tasks`.
- Cómo validarlo: inspeccionar el almacenamiento del navegador en un entorno local de prueba y revisar el flujo login→tareas; confirmar si el riesgo justifica cambiar el mecanismo de sesión.

### H-WEB-07: El parseo del usuario persistido puede abortar la inicialización del dashboard
- Estado: CANDIDATO
- Evidencia: `web/src/app/services/auth.service.ts:53` parsea el usuario sin `try/catch`; `web/src/app/dashboard/dashboard.component.ts:46` lo llama antes del `try` de la consulta, que empieza en la línea 52; `loading` inicia en `true` en la línea 29.
- Impacto: un valor persistido que no sea JSON válido puede rechazar `ngOnInit()` antes del manejo de errores de tareas y dejar el estado de carga activo.
- Prioridad propuesta: baja.
- Contrato potencialmente afectado: recuperación de la sesión local al entrar a `/dashboard`; no se identificó un contrato de recuperación acordado.
- Cómo validarlo: prueba con un valor de usuario local malformado; observar si `ngOnInit()` rechaza y `loading` queda activo, y acordar el comportamiento esperado.

### H-WEB-08: El valor `owner` se interpola directamente en la URL de tareas
- Estado: CANDIDATO
- Evidencia: `web/src/app/services/tasks.service.ts:9` concatena `owner` al query; `web/src/app/dashboard/dashboard.component.ts:53` pasa el username; `web/src/app/login/login.component.ts:29` solo comprueba que no esté vacío.
- Impacto: si se admiten usernames con caracteres reservados, el query puede interpretarse de forma distinta al owner pretendido. No se encontró una regla que confirme si esos caracteres están permitidos.
- Prioridad propuesta: baja, pendiente de confirmar el formato admitido.
- Contrato potencialmente afectado: parámetro `owner` de `GET /api/tasks`.
- Cómo validarlo: prueba unitaria de `TasksService` con un username de prueba que contenga caracteres reservados; comparar la URL resultante con la serialización requerida por el contrato acordado.

### H-WEB-09: La consulta de tareas no configura un timeout
- Estado: CANDIDATO
- Evidencia: `web/src/app/services/tasks.service.ts:9` invoca Axios sin configuración de timeout; `web/src/app/dashboard/dashboard.component.ts:29` inicializa `loading` en `true` y solo lo cambia en las ramas de resolución y rechazo, líneas 70 y 76.
- Impacto: si la petición queda pendiente sin resolver ni rechazar, el dashboard puede permanecer indefinidamente en estado de carga. No se encontró un límite temporal acordado.
- Prioridad propuesta: baja, pendiente de definir el límite esperado.
- Contrato potencialmente afectado: disponibilidad y tiempo de respuesta observados al consultar `GET /api/tasks`.
- Cómo validarlo: simular una petición que no resuelve ni rechaza y comprobar el estado de carga; acordar un límite antes de establecer una expectativa temporal automatizada.
